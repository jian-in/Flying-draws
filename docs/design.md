# Sketchlink 设计草案

> 暂定名，发布前需要查一下 GitHub 和 npm 上有没有重名。
> 版本：v0.1 草案 · 2026-11-14

## 1. 一句话

一个本地桌面画布，用 MCP 接到任何 agent 上。用户能用画来表达想法，agent 能读懂画里的结构，也能把自己的理解画回来让用户确认。

## 2. 要解决的问题

有些想法打字很费劲，画两笔就清楚了，比如流程、布局、位置关系、趋势曲线，或者在截图上圈一下"这里"。现在的 agent 基本只能收文字和图片。用户画了图也只能截图发过去，agent 拿到的是一堆像素，看不出框和框之间是怎么连的。

### 已有方案和它们的不足

| 方案 | 做了什么 | 缺什么 |
|---|---|---|
| tldraw MCP App（2026-03） | agent 写 JS 在 tldraw 画布上画，用户的修改会同步回来 | 画布只能在支持 MCP Apps 的宿主里显示，命令行 agent 用不了（实测 `exec` 只返回"正在渲染"，不给可打开的地址）；agent 要先查 API 再写代码，很费 token；画布状态存在 tldraw 云端；SDK 正式上线需要许可证 |
| tldraw Agent starter kit | 完整的"一起画、一起聊"体验 | 是一个独立应用，自己调模型，接不进用户现有的 agent |
| Sketchpad | 打开 Excalidraw 画布，画完导出 PNG 给 agent | 只给图片，不给结构；只能用户主动发起 |
| Make Real | 画界面草图，生成网页 | 只有"草图到代码"一条路，不能来回对话 |
| Excalidraw MCP 系列 | agent 往画布上画图 | 只能 agent 画给用户看 |

### 我们的差异点

1. **什么 agent 都能接**：画布是一个独立的桌面窗口，跟宿主支不支持嵌入界面无关。
2. **给 agent 的是能直接理解的结构**：把画布翻译成简洁的语义描述（节点、连线、标注、分组、手绘笔画），同时附一张渲染图。
3. **用画来对话**：agent 可以主动请用户画；也可以把自己的理解画在"提议层"上，等用户确认或修改。
4. **全本地、MIT 开源**：画的内容不离开本机，应用里不内置任何模型，不需要 API key。

## 3. 设计原则

- **agent 负责想，画布负责收和发。** 应用不调用任何大模型，理解和推理都交给接进来的 agent。这样不用配 key，也不绑定任何一家厂商。
- **结构优先，图片兜底。** 能从数据里读出来的（文字、连线、包含关系）就直接给结构；读不出来的（手绘涂鸦）给图片，交给 agent 的视觉能力。
- **分清谁画的。** 每个元素都记录作者（用户 / agent）和所在层（正式层 / 提议层），用颜色区分，agent 读取时也会说明。
- **工具要少，参数要高层。** agent 只需要说"加一个节点、连一条线"，坐标和排版由应用自动处理。

## 4. 核心使用流程

### 流程 A：用户主动画，然后发送
1. 用户在画布上画，比如一个流程草图。
2. 点"发给 agent"，可以附一句话。
3. 下次 agent 调用 `canvas_read` 或 `canvas_wait` 时，拿到语义描述、渲染图和这句附言。

### 流程 B：agent 请用户画
1. agent 调用 `canvas_request(prompt="把你想要的页面布局画一下")`。
2. 画布窗口跳到前台，顶部显示这条请求。
3. 用户画完点"发送"，agent 通过 `canvas_wait` 拿到结果。

### 流程 C：agent 画出理解，用户确认（核心体验）
1. agent 读完用户的草图，调用 `canvas_propose(ops, question="你是这个意思吗？")`。
2. agent 的理解画在提议层上，用半透明的另一种颜色显示，不覆盖用户的原图。
3. 用户可以点"对"，也可以直接在上面改（划掉、拖动、补一笔），然后发送。
4. agent 拿到的是"接受 / 修改"的结果和具体改了哪些地方（diff）。接受的内容会合并进正式层。

### 流程 D：在截图或图片上标注
1. agent 调用 `canvas_request(image=<截图>, prompt="圈出要改的地方")`。
2. 用户在图上圈、画箭头、写字。
3. agent 拿到每个标注对应的图片区域坐标和附近的文字。

## 5. 架构

```
┌──────────────┐  stdio MCP   ┌─────────────────┐  WebSocket   ┌─────────────────────────┐
│ 任意 agent    │ ───────────▶ │ sketchlink-mcp  │ ───────────▶ │ Sketchlink 桌面应用       │
│ Claude Code   │              │ （轻量桥接进程）  │  127.0.0.1   │  ├ 主进程：本地服务、存储   │
│ Codex / Cursor│  HTTP MCP    │                 │  + token     │  ├ 渲染进程：Excalidraw    │
│ Gemini CLI ...│ ────────────────────────────────────────────▶ │  └ 语义层：画布 → 描述      │
└──────────────┘  （可选，直连） └─────────────────┘              └─────────────────────────┘
```

- **桌面应用**：常驻运行，负责画布窗口、本地存储和语义翻译。主进程在 `127.0.0.1` 上开一个 WebSocket 服务，同时提供 Streamable HTTP 的 MCP 端点，给支持 HTTP 的 agent 直连。
- **sketchlink-mcp 桥接**：agent 通过 stdio 启动的一个小进程，只负责转发。连接时如果发现桌面应用没在运行，就自动把它拉起来。用 `npx sketchlink-mcp` 就能装。
- **为什么拆成两个进程**：stdio MCP 进程的生命周期由 agent 控制，agent 一退出它就没了。画布要比单次会话活得久，多个 agent 也要能同时连到同一块画布上。

### 技术选型

| 部分 | 选择 | 理由 |
|---|---|---|
| 桌面壳 | Electron（第一版） | 全部用 TypeScript 写，一门语言打通前端、主进程和 MCP；Excalidraw 本身就是 React 组件，直接嵌进去。Tauri 安装包更小，但要额外写 Rust，等稳定以后再考虑迁移 |
| 画布 | Excalidraw（MIT） | 许可证干净；元素数据自带连线绑定和文字容器关系，方便做语义层；内置 `embeddable` 和 `iframe` 元素，可以嵌网页 |
| MCP | 官方 TypeScript SDK | 同时支持 stdio 和 Streamable HTTP |
| 存储 | 本地 JSON 文件 | 每块画板是一个 `.excalidraw` 文件，另存一份版本历史；用户可以直接拿去 excalidraw.com 打开 |
| 自动排版 | ELK.js 或 dagre | agent 只给节点和连线，坐标由应用算 |

## 6. 语义层（"可理解"的核心）

把 Excalidraw 的场景数据翻译成 agent 好读的描述，分三层输出。

### 6.1 结构提取规则
- **节点**：矩形、椭圆、菱形，以及里面绑定的文字（文字元素用 `containerId` 指向容器）。
- **连线**：箭头的 `startBinding` 和 `endBinding` 指向两端元素，箭头上绑定的文字就是连线标签。
- **游离文字**：没有绑定容器的文字，按距离挂到最近的节点或连线上，作为"旁注"。
- **分组和包含**：`groupIds`、frame，以及几何上的包含关系（一个框完全套住另一个框）。
- **手绘笔画（freedraw）**：按空间位置聚类，给每簇算出外接框，用简单几何判断大致形状（直线、曲线、圈、叉、勾）。判断不了的标成"涂鸦"，交给 agent 看图。
- **圈选标注**：一个圈套住了图片的某块区域时，输出"用户圈出了图片的 (x, y, w, h) 区域"，并换算成原图坐标。
- **曲线**：用户画的单条曲线可以按需导出成采样点序列，供"按这个形状调参数"这类任务使用。

### 6.2 输出格式（三选一或组合）
- `summary`：几行自然语言加缩进列表，最省 token，默认返回这个。
  ```
  画板「登录流程」v12（用户画 9 个元素，agent 画 3 个元素）
  节点：[A]打开 App → [B]是否已登录？ → 是：[C]首页 / 否：[D]登录页
  旁注："D 要支持扫码"（靠近 D）
  手绘：B 右侧有一个问号形状的涂鸦（未识别）
  ```
- `graph`：JSON 格式的节点、边、旁注、分组，适合 agent 用程序处理。
- `image`：PNG 渲染图。默认只在存在未识别涂鸦或图片标注时附上。

### 6.3 增量
每次修改版本号加一。`canvas_read(since=v)` 只返回从 v 之后的变化，比如"新增 2 个节点，删除 1 条连线，用户修改了提议层里的 C"。

## 7. MCP 工具草案

| 工具 | 作用 | 是否阻塞 |
|---|---|---|
| `canvas_open(board?, title?)` | 打开或新建画板，把窗口带到前台 | 否 |
| `canvas_read(board, format?, since?)` | 读取当前画板（summary / graph / image），返回带版本号 | 否 |
| `canvas_request(prompt, board?, image?, mode?)` | 请用户画或标注，返回 `request_id` | 否 |
| `canvas_wait(request_id 或 board, timeout_s≤45)` | 等用户点"发送"，超时就返回 `status: waiting`，agent 再调一次 | 最多 45 秒 |
| `canvas_draw(board, base_version, ops[])` | 在正式层上画；版本冲突时整批拒绝（见第 12 节） | 否 |
| `canvas_propose(board, base_version, ops[], question)` | 在提议层上画，返回 `request_id`，用 `canvas_wait` 等用户确认 | 否 |
| `canvas_list()` | 列出画板 | 否 |

`ops` 是一组高层操作：`add_node`、`add_edge`、`add_text`、`add_image`、`add_embed`（网页、代码块、Markdown 卡片）、`move`、`update`、`delete`、`group`、`highlight`，可以带 `layout: "auto"`。

**为什么要拆出 `canvas_wait`**：用户画图可能要好几分钟，但已知的 MCP 客户端超时情况很杂。有用户报告 Claude Code 的 HTTP 传输写死了 60 秒，桌面 app 的 stdio 调用约 60 秒就会被取消。把"发起请求"和"等待结果"分成两个工具，每次最多等 45 秒，在哪种客户端上都不会撞上超时。

**MCP Resources（可选）**：`sketchlink://boards`、`sketchlink://board/{id}/summary`。用户点"发送"时推送资源更新通知，给支持订阅的客户端用。

## 8. 嵌入和编辑

画布上除了图形，还能放这些可编辑的块：
- **图片和截图**：可以拖进来、粘贴，也可以由 agent 发送；可以在上面标注。
- **代码块**：带语法高亮，用户能直接改，agent 读取时拿到的是原文。
- **Markdown 卡片**：写备注、需求、清单。
- **网页预览**：用 Excalidraw 的 `embeddable` 元素嵌入，比如本地开发服务器的页面。

所有块对语义层都是"带内容的节点"，agent 读到的是里面的文字内容，不只是一张图。

## 9. 数据和隐私

- 画板存在 `~/.sketchlink/boards/`，每块画板一个 `.excalidraw` 文件，旁边放一个版本历史目录。
- 元素的来源（作者、图层、对应的请求 ID）写在 Excalidraw 元素的 `customData` 字段里，导出后其他 Excalidraw 也能正常打开。（`customData` 的具体用法要在 Excalidraw 源码里确认。）
- 本地服务只绑定 `127.0.0.1`。桥接进程连接时要带一个随机 token，token 存在用户目录下，防止本机其他网页直接连进来改画布。
- 不收集任何遥测数据。

## 11. 怎么判断"可理解"做到了

做一个小评测集：30 到 50 张典型草图（流程图、布局、带圈选的截图、带注释的曲线），每张写好标准答案。对比两种做法：只给 agent 图片，以及给图片加语义描述。比较 agent 复述的准确率和花的 token。这个结果也可以直接放进 README，用数据说明"为什么不只发截图"。

## 12. 并发和冲突

多个写者共用一块画板：用户本人，加上一个或多个 agent。这本质上是读者写者问题，要处理的有三件事：读到改了一半的状态、丢失更新、写者饥饿。另外还要防止人和 agent 互相干等。

### 12.1 读：快照，不加锁
- 画板每次修改，版本号 `version` 加一。`canvas_read` 返回某个版本的完整快照，并带上这个版本号。
- 快照在主进程里一次生成，读的过程中不会有写入插进来，所以读者永远读不到改了一半的状态，也不需要读锁。

### 12.2 写：主进程串行执行
- 所有修改，包括用户在渲染进程里的编辑和 agent 通过 MCP 发来的 ops，都要经过主进程的一个写队列，按顺序执行。
- 一批 ops 作为一个整体执行：要么全部生效，要么全部不生效，版本号只加一次。

### 12.3 丢失更新：乐观并发
- `canvas_draw` 和 `canvas_propose` 必须带上 `base_version`，也就是 agent 最后一次读到的版本号。
- 执行前检查：这批 ops 要改或要删的元素，从 `base_version` 之后有没有被别人动过。
  - 没动过：直接执行。中间别处有新增内容不影响，不算冲突。
  - 动过：整批拒绝，返回 `conflict`，附上这些元素从 `base_version` 到当前版本的变化。agent 读完变化，按新状态重新生成 ops 再提交。
- 只新增元素的 ops 不会冲突。自动排版如果要挪动已有元素，按"修改"处理，同样要检查。

### 12.4 用户优先，防止饿到用户
- 用户正在画一笔（鼠标或笔还没抬起）、正在拖动或正在编辑文字时，agent 的写入在队列里等着，等这个动作结束后再执行。
- agent 不能直接修改或删除作者是用户的元素，只能在提议层上画。要改用户画的东西，就用 `canvas_propose` 提出来，用户接受后才合并进正式层。用户的原图因此不会被 agent 改坏。
- 反过来也要防止 agent 被饿死：用户一直在画，agent 的写入在队列里等超过 10 秒，就在画布上提示"agent 有内容要画"，由用户决定先停一下还是继续。

### 12.5 多个 agent 之间
- 每个连进来的 agent 有自己的 `agent_id` 和颜色，提议层按 agent 分开显示。
- 不同 agent 之间的写入也走 12.3 的版本检查。一个 agent 不能修改另一个 agent 画的元素，只能提议，由用户裁决。
- 不存在多把锁，也没有谁持有资源去等别人，所以系统内部不会形成循环等待。

### 12.6 人和 agent 互相干等
真正可能"卡住"的地方在人和 agent 之间：agent 调了 `canvas_wait` 在等用户，用户却以为该轮到 agent，两边都不动。
- 画布顶部固定显示一个状态条，说明现在在等谁：`agent 正在等你：把页面布局画一下`，或者 `agent 正在处理…`，或者 `空闲`。
- `canvas_wait` 超时返回时带上 `waiting_for: "user"`。agent 连续几次都等不到，就应该在对话里提醒用户，而不是一直静默重试。工具描述里要写明这一点。
- 用户可以在状态条上点"取消这个请求"，`canvas_wait` 会立刻返回 `status: cancelled`。

## 13. 风险和待定问题

- **竞争**：tldraw 官方在做同类方向。我们的立足点是本地运行、开源、什么 agent 都能接、语义层更深，README 第一屏要把这几点讲清楚。
- **超时**：各家客户端的工具超时行为不一样，`canvas_wait` 的 45 秒上限要在 Claude Code、Codex、Cursor 上逐个实测。
- **手绘识别**：纯几何规则只能认出简单形状，复杂涂鸦交给 agent 看图。要不要在本地加一个小模型，等 M4 再决定。
- **学习成本**：项目主体是 TypeScript 和 React，需要先补前端基础。M0 的规模刻意压得很小，就是为了边做边学。
- **跨平台**：先保证 Windows 能用，macOS 和 Linux 的安装包放到 M2 以后。
- **待定**：项目名；画布窗口默认悬浮在最上层还是普通窗口；agent 写入等待多久算"被饿到"（12.4 先定 10 秒，要实测调整）。
